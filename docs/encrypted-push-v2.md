# Enrollment v2: endpoint updates over Signal

This extends the [private enrollment operator guide](encrypted-push-server-v1.md).
The authoritative wire format, schemas and synthetic interoperability vector
are in [the v2 contract](../contracts/encrypted-push/v2/README.md).

## What changes

A phone can change its push endpoint, `p256dh` receiver public key and `auth`
secret through the server's existing outgoing Signal websocket. This requires
no inbound server port. The phone sends to its own Signal account with
`urgent=false`; only CollieSocket's linked-device copy contains the encrypted
control blob. Other linked devices receive an ordinary Signal sync message.

The blob uses an independent 32-byte AES-GCM control key generated by the phone.
Only authenticated decryption authorizes an update. Sender metadata is not
trusted. The account, device ID, password, instance and control key remain
private-import-only values. Existing destination checks and encrypted delivery
requirements apply to every updated endpoint.

## Enroll or migrate

1. Stop the service and back up its protected state using the existing operator
   procedure. Run `mollysocket migrate` with the service account and configuration.
   This version reports `{"schema_version":3}`. The additive migration preserves
   existing subscriptions, queues and private-import receipts.
2. Export enrollment v2 from a compatible phone. Keep that export private: it
   contains the Signal password, Web Push secret and new control key. Import it
   using the existing protected file or pipe workflow. Never put its contents
   in a URL, issue, log or command-line argument.
3. For a new account, use epoch 1. To enable control for an existing v1 account,
   import the next epoch with `enrollment_version: 2`, `control_key`, and
   `supported_event_versions: [2]`. The receipt selects event version 2 without
   returning the key. V1 and keyless v2 enrollments continue to select version 1.
4. Restart the service after migration. Later private imports are detected by
   the connection manager, including a control-key rotation that leaves the
   Signal credentials and endpoint unchanged.

Older binaries do not understand schema 3. To roll back the binary, stop the
service and restore its compatible pre-migration backup. Do not lower SQLite's
`user_version` or remove tables to force an older binary to open the new state.

## Confirmation and retries

The phone persists one pending update and its exact encrypted bytes before
sending. The server authenticates the blob and commits the new subscription,
epoch and status outbox entry in one transaction before acknowledging the Signal
frame. A valid next-epoch update can recover a stale subscription. An ordinary
message on the same socket then uses the new endpoint and Web Push keys.

The phone completes the change only after receiving a valid encrypted version-2
`status` event with code `subscription_updated`, the pending epoch and its
instance, through the pending subscription. Signal send success and provider
HTTP 2xx are not phone receipt. Until confirmation, it resends the same bytes.

An identical current-epoch retry does not change the subscription or reactivate
stale state. It preserves any pending confirmation. If the previous confirmation
was lost after provider acceptance or expired, a retry may enqueue one replacement
status, at most once per 30 seconds. This limit survives a service restart.
Conflicting same-epoch, old, skipped, malformed and forged controls have no
subscription effect and never fall through to an ordinary wake.

Changing the password, account, device ID, instance, control key or negotiated
event version requires a new private import. After restoring or replacing phone
state, use fresh receiver keys, instance and control key through private import
before sending resumes.

## Verification

Run the repository checks from `AGENTS.md`, plus:

```sh
python3 contracts/encrypted-push/v2/tools/conformance.py
```

`cargo test --locked` includes an actual loopback Signal websocket and HTTP push
provider. It verifies an authenticated endpoint/key change, stale recovery,
durable commit before ACK, replay/forgery rejection, the next push on the existing
socket, and rollback without ACK when outbox persistence fails. An independent
OpenSSL receiver decrypts the resulting Web Push messages. The CLI suite also
checks v1/keyless compatibility, v2 negotiation and control-key redaction.

These synthetic checks do not claim real Signal service delivery, physical
Android receipt, or deployment acceptance.
